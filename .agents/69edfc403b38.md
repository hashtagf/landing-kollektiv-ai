# Plan: Fix Railway build (npm EBUSY) and clean up cutover follow-ups

## Summary
Drop `npm ci &&` from `railway.json`'s `buildCommand` so Nixpacks runs install and build in separate layers — this resolves the `npm error code EBUSY` that fails the Railway Docker build. Also pick up the minor cleanup items from the prior review.

## Approach
The Nixpacks-generated Dockerfile mounts both `/app/.next/cache` and `/app/node_modules/.cache` as cache volumes on the build RUN. Because we set `buildCommand: "npm ci && npm run build"`, those two mounts are present during `npm ci`. `npm ci` tries to remove and recreate `node_modules`, but `node_modules/.cache` is a live mount — the directory cannot be unlinked, so npm errors with `EBUSY` and the build fails at Dockerfile:24.

The fix is to let Nixpacks handle install in its own dedicated layer (where only the npm download cache is mounted, not `node_modules/.cache`) and limit `buildCommand` to `npm run build`. Nixpacks auto-detects Next.js and already runs `npm ci` from the lockfile in the install phase, so this is purely removing a redundant, harmful step — not skipping installation.

While we're touching deploy plumbing, also align the CI `build-test` job's start invocation with the Railway start command (`npm start -- -p ${PORT:-3000}`) so CI exercises the same startup path as production, and re-sync `.wolf/anatomy.md` to point at the actual runbook location (`docs/runbooks/`, not `.kollektiv/runbooks/`).

## Files to touch
- `railway.json` — change `build.buildCommand` from `"npm ci && npm run build"` to `"npm run build"`. Leave `startCommand`, `healthcheckPath`, restart policy untouched.
- `.github/workflows/ci-cd.yml` — in the `build-test` job, replace `run: npm run start &` + `env: PORT: 3000` with `run: npm start -- -p 3000 &` so CI mirrors the Railway start syntax. Keep the `sleep 10` + curl healthcheck + pkill teardown.
- `.wolf/anatomy.md` — fix the `.kollektiv/runbooks/` entry to reflect the runbook's real path under `docs/runbooks/railway-cutover.md`.
